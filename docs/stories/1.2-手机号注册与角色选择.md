## Story

**As a** 校共体平台的潜在用户（教师 / 教育管理人员 / 研究人员等）,
**I want** 通过手机号 + 短信验证码 + 用户名 + 角色身份完成注册,
**so that** 我能以正确的角色身份进入平台，后续接收符合身份的政策内容与推荐。

---

## Epic Context

**Epic 1 - 基础设施与用户系统**

建立项目基础设施（前后端框架、数据库、缓存），实现完整的用户系统，包括手机号注册/登录、角色选择、JWT 认证保持登录、使用日志记录。此 Epic 是所有后续功能的基础依赖。

**Story 1.2 Deliverables:**

- `users` 表创建（Flyway `V1__create_users.sql`，部署在 `edu-core`）
- 6 种角色枚举 `UserRole` + 用户类型枚举 `UserType`（`edu-common.constant`）
- `POST /api/auth/send-sms` 短信验证码发送接口（含 60s/手机号频率限制）
- `POST /api/auth/register` 手机号注册接口（验证码校验 + 用户名/角色校验 + 唯一性校验）
- `SmsService` 接口 + 默认 `LogSmsService`（dev/test 实现，生产实现由后续 Story 接入）
- 验证码缓存 Redis 设计（`sms:code:{phone}` 5min / `sms:limit:{phone}` 60s）
- 前端 `RegisterView.vue` 注册页（表单 + 6 卡片角色选择 + 60s 倒计时按钮）
- 前端 `src/api/auth.ts`（`sendSms()` / `register()` 调用封装）
- 前端响应式 + 移动端 44px 触控目标基线已建立（来自 1.1）
- 清理 1.1 遗留 `backend/backend/` 孤立目录（QA Round-1 LOW issue 1）

## Acceptance Criteria

### AC1: 手机号注册

**Scenario**
```gherkin
GIVEN 用户未注册
WHEN 用户输入手机号、验证码、用户名、选择角色并提交注册
THEN
  - 用户记录创建到数据库
  - 密码/验证码安全处理
  - 返回注册成功并引导登录
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-1.1 | 手机号必须唯一，不可重复注册 |
| BR-1.2 | 角色为必选项，可选值：区域教育管理人员、校共体核心牵头校人员、校共体成员校人员（城镇）、校共体成员校人员（乡村）、研究人员、其他人员 |
| BR-1.3 | 用户名为必填项，2-20 个字符 |

**Data Validation**
| Field | Type | Required | Rules | Error Message |
|-------|------|----------|-------|---------------|
| phone | string | true | 中国大陆手机号格式，11 位数字，1 开头 | 请输入正确的手机号 |
| sms_code | string | true | 6 位数字验证码，5 分钟有效期 | 验证码错误或已过期 |
| username | string | true | 2-20 个字符 | 用户名需 2-20 个字符 |
| role | string | true | 枚举值，必须为 6 种角色之一 | 请选择您的角色身份 |

**Error Handling**

> ⚠️ **响应码语义（M2 修订）**：下表 `Code` 列为**业务响应体 `R.code`**（即 `BizException(code, msg)` 的构造参数），**非 HTTP 状态码**。所有业务异常经 1.1 `GlobalExceptionHandler` 统一返回 **HTTP 200 + `R(code, message, null)`**。前端 `handleResponseError` 必须依据 `R.code` 分支。

| Scenario | R.code | Message | Action |
|----------|--------|---------|--------|
| 手机号已注册 | 409 | 该手机号已注册，请直接登录 | 返回错误，提供登录入口链接 |
| 验证码错误 | 400 | 验证码错误或已过期，请重新获取 | 清空验证码输入框，允许重新获取 |
| 短信发送失败 | 503 | 短信发送失败，请稍后重试 | 记录日志，60 秒后允许重新发送 |
| 字段格式校验失败（手机号 / 用户名 / 验证码长度等） | 4000 | 由 Spring Validation 拼接首个字段错误 message | 前端按 4000 提示对应字段错误，红色高亮 |
| 60s 内重复请求验证码 | 429 | 验证码已发送，请稍后再试 | 按钮维持倒计时，禁止再次请求 |

**UI Interaction**
| Trigger | Behavior |
|---------|----------|
| 点击获取验证码 | 发送短信，按钮变为 60 秒倒计时 |
| 提交注册 | 显示加载状态，成功后跳转登录页 |

**Examples**
- **Input**: 手机号: 13800138000, 验证码: 123456, 用户名: 张老师, 角色: 校共体成员校人员（乡村）
  **Expected**: 注册成功，跳转至登录页

### AC2: 角色选择界面

**Scenario**
```gherkin
GIVEN 用户在注册页面
WHEN 用户进入角色选择步骤
THEN
  - 展示 6 种角色选项，每个角色附带简短说明
  - 用户选择后角色标签高亮
  - 角色选择结果随注册信息一起提交
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-2.1 | 必须选择且只能选择一个角色 |
| BR-2.2 | 角色选择后可在个人设置中修改（个人设置在后续 Story 实现，本 Story 仅完成首次选择） |

**Error Handling**

> ⚠️ **响应码语义**：同 AC1 — `Code` 为业务 `R.code`，HTTP 状态恒为 200。

| Scenario | R.code | Message | Action |
|----------|--------|---------|--------|
| 未选择角色直接提交（`@NotBlank role` 触发 Spring Validation） | 4000 | 请选择您的角色身份 | 角色选择区域高亮提示 |
| 角色枚举值非法（绕过前端、传入未知值） | 400 | 请选择您的角色身份 | 由 `AuthService` 显式 `throw new BizException(400, ...)` |

## Dev Notes

### Technical Constraints

- **PostgreSQL 主键策略**：`users.id` 使用 `UUID PRIMARY KEY DEFAULT gen_random_uuid()`，需 `pgcrypto` 扩展（PG 16 默认包含 `gen_random_uuid()` 无需启用 pgcrypto，但若部署到旧版本需 `CREATE EXTENSION pgcrypto`；Story 1.1 已启用 vector + zhparser，gen_random_uuid 可直接使用）`[Source: docs/fullstack-architecture/database-schema.md §7.1, §7.2]`
- **JWT 与登录会话不在本 Story**：注册成功**仅返回 UserDto**（不签发 Token），Token / 登录由 Story 1.3 实现，因此本 Story 不引入 `spring-boot-starter-security` 与 `JwtProvider`；`AuthController` 暂无 `@PreAuthorize`（接口为公开访问）`[Source: docs/prd/epic-1-基础设施与用户系统.md Story 1.3]`
- **password_hash 字段保留**：表结构含 `password_hash VARCHAR(255)` 但本 Story **不写入**（始终为 NULL），未来若启用密码登录复用此列 `[Source: docs/fullstack-architecture/database-schema.md §7.2]`
- **手机号唯一性双重保障**：① DB 层 `UNIQUE` 约束 ② Service 层 `existsByPhone` 预检（避免抛裸 `DataIntegrityViolationException`）；并发场景下若预检通过、写入冲突，由 `GlobalExceptionHandler` 兜底为 409
- **敏感数据日志**：禁止在日志中输出**完整手机号**与**验证码内容**；`LogSmsService` 仅在 dev/test profile 输出验证码以便手工调试，prod profile 必须由真实 Provider 替换（依据 `docs/fullstack-architecture/security.md` 第 14 节 "敏感数据" 行的精神，本 Story 据此细化为"禁止完整手机号 / 验证码入日志"具体规则）
- **Redis 键过期 TTL 严格遵守**：`sms:code:{phone}` SETEX 300s（5min）、`sms:limit:{phone}` SETEX 60s；写入采用 SET ... NX EX 60 实现"60s 内首次写入即占位"语义（避免使用 `INCR`/`EXPIRE` 两步非原子操作）`[Source: docs/fullstack-architecture/8-redis-设计.md §8.1]`
- **DTO 不暴露 Entity**：`UserDto` 不含 `passwordHash`、不含 `lastLoginAt`（无意义于注册响应），符合 coding-standards "Entity 不出现在 Controller 层" `[Source: docs/fullstack-architecture/coding-standards.md#分层约定]`
- **Spring Validation 错误统一收口**：依赖 1.1 的 `GlobalExceptionHandler` 已捕获 `MethodArgumentNotValidException` 并转换为 **HTTP 200 + `R.fail(4000, "{字段错误拼接}")`**（业务码源自 1.1 `GlobalExceptionHandler.CODE_VALIDATION = 4000`）。因此 DTO 字段的 `message` 文案需直接对齐 AC1 数据校验表；前端 `handleResponseError` 必须依据 **`R.code` 分支**（`4000` 表示参数错误），**不可**基于 HTTP status，因为统一返回 200
- **接口路径必须落到 edu-core**：`/api/auth/**` 隶属 edu-core 模块；Gateway 路由规则待"可观测性 / 路由配置 Story"细化，本 Story 期间通过 `edu-core` 直连端口 :8081 验证 `[Source: docs/fullstack-architecture/rest-api-spec.md §9.4]`

### Database Design

**新增表**：`users`（部署在 `edu-core` 模块的 Flyway migration `V1__create_users.sql`）

设计要点：
- 主键 `id` 使用 `UUID DEFAULT gen_random_uuid()` — 与全局规范一致 `[Source: docs/fullstack-architecture/database-schema.md §7.2]`
- `phone VARCHAR(11) UNIQUE` — DB 层强制唯一 + Service 层预检
- `role VARCHAR(30)` — 使用字符串存枚举名，便于后续新增角色不需要 ALTER 类型；不使用 PostgreSQL ENUM 类型（避免后续添加值需要 ALTER TYPE 锁表）
- `user_type VARCHAR(10) NOT NULL DEFAULT 'USER'` — 注册创建的均为普通用户；ADMIN 通过运营后台创建（Epic 6）
- `region VARCHAR(100)`、`school VARCHAR(100)` — 注册阶段不强制采集（架构表保留），本 Story 写 NULL
- `password_hash VARCHAR(255) NULLABLE` — 当前验证码登录，留作密码登录扩展
- `created_at / updated_at TIMESTAMPTZ NOT NULL DEFAULT now()` — 更新由应用层 `@PreUpdate` 维护
- `last_login_at TIMESTAMPTZ NULLABLE` — Story 1.3 登录时更新

**索引**：
- `idx_users_phone (phone)` — 登录与去重查询主入口
- `idx_users_role (role)` — 后续按角色聚合 / 推荐查询用 `[Source: docs/fullstack-architecture/database-schema.md §7.2]`

**迁移文件**：
- `backend/edu-core/src/main/resources/db/migration/V1__create_users.sql` — 与 source-tree 命名约定一致 `[Source: docs/fullstack-architecture/source-tree.md "数据库迁移 (Flyway)"]`

### Implementation Summary

按 13 个子任务线性推进（T0→T13），TDD 红→绿：每个后端 Service/Controller 与前端组件先补齐测试骨架，再实现生产代码通过。关键决策：
1. **Architect L3 采纳**：`SmsService.sendVerificationCode` 改为 `void`，通过 `RedisTemplate` 的 Mockito `verify` 断言交互而非返回值，避免验证码沿返回值外溢。
2. **响应契约固化（Architect M2）**：所有业务异常 `throw new BizException(code, msg)` 交由 1.1 `GlobalExceptionHandler` 统一返回 HTTP 200 + `R.fail(code, msg)`；仅未捕获 `Exception` 返回 HTTP 500 + `R(5000, "系统繁忙，请稍后再试")`。
3. **验证码原子频率限制**：`redisTemplate.opsForValue().setIfAbsent(key, val, Duration.ofSeconds(60))` 单步 SET NX EX，规避 SET+EXPIRE 两步非原子漏洞。
4. **双击 / 并发防护**：`RegisterView.submitting.value = true` 提前到 `await validate()` 之前；`BizException(429)` 频率限制 + DB `UNIQUE(phone)` + `verifyCode` 一次性 `DEL` 三重并发防护。
5. **Docker 可选**：`@Testcontainers(disabledWithoutDocker=true)` 在无 Docker 沙盒优雅跳过 18 个集成测试；CI 具备 Docker 时自动启用。
6. **敏感数据多层守护**：`UserDto` 白名单字段 + Jackson 序列化 + 反射断言 + 日志脱敏 `138****8000`。

**测试结果**：后端 46 tests（28 pass + 18 Docker-gated skipped） / 前端 31 tests（全部 PASS） / `mvn -B test` + `vitest run` + `npm run build` 全绿。

- **L3（新）：`SmsService.sendVerificationCode` 接口签名返回 `String` 暴露验证码敏感数据**
  - **Location**: 行 174（T3 第一子任务接口定义）
  - **Description**：接口签名 `String sendVerificationCode(String phone)` 虽注释"实际下游不返回敏感数据"，但 `String` 返回类型使调用链（`AuthController` → 日志 / 响应 / 监控）存在**误写入日志**的失误面；与 Dev Notes 行 268 "禁止在日志中输出**完整手机号**与**验证码内容**" 约束隐含冲突。测试断言可通过 Mockito `verify(redisTemplate.opsForValue()).set(eq("sms:code:"+phone), anyString(), eq(Duration.ofMinutes(5)))` 完成，不必依赖返回值。
  - **Recommendation**：Dev 在 T3 实施时将接口改为 `void sendVerificationCode(String phone)`（或 `boolean` 表示"是否成功占位"），`SmsServiceTest` 用 ArgumentCaptor / verify 断言 Redis 交互而非返回值。此项不阻塞 Round 2 通过，但建议 QA test-design 在"敏感数据不出接口边界"测试点显式覆盖。

- **L4（新）：Data Synchronization Requirements §4 交叉引用错位**
  - **Location**: 行 389 "T4 步骤④已显式包含 'register 成功后删除 `sms:code:{phone}`'，无遗漏"
  - **Description**：T4 步骤④实际描述为 `userRepository.save(new User(...))` （行 183）；验证码 Redis 清理发生在 `SmsService.verifyCode()`（T3 明确 "验证码一次性消费（成功后立即从 Redis 删除）"），不在 T4 ④。文字表述指错步骤。
  - **Recommendation**：将 §4 第一项改为 "SmsService.verifyCode 已内建 '验证成功后 DEL sms:code:{phone}' 的一次性消费语义（T3 明确）；T4 步骤① `smsService.verifyCode` 调用即覆盖该清理。" 或把 T4 步骤①括注补足 "成功路径内部 DEL sms:code:{phone}"。此项不阻塞实现，可由 Dev 在实施期顺手修订，或 SM 在下一轮 Story 维护中处理。
